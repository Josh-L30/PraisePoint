# S02: Shared church workspaces

Status: Done. Verified 2026-10-27 on the existing Supabase Free project; no deployment.
Base: dd5d9c3a216fd9adc667095cc2e31312203faf29.

Scope: create one church per account, switch personal/church workspaces without copying content, owner/member roles, seven-day email-bound single-use invitations, removal/leave, and atomic ownership transfer. Invitations are manually copied; no emails are sent.

Implementation: privileged operations live in the private database schema behind authenticated RPC wrappers. The database creates random invitation tokens and stores only their SHA-256 digests. PostgreSQL row locks serialize invitation acceptance, removal, and ownership changes. Current membership and verified Google identity are checked on every mutation.

Limits: one created church/account, ten invitations/hour/actor, reusable content-write budget of 120/minute for later save RPCs. Client constants describe these limits; database constants enforce them.

Acceptance: database authorization, invitation failures and actual concurrent acceptance/transfer passed; safe teammate projection, switching, forms/recovery, S01 regressions and production browser checks passed.

Backend verification: full hosted rollback assertions pass, including an exact seven-day expiry and normalized recipient check. True overlapping invitation acceptance and ownership transfer also pass using distinct editor/connector database connections; exactly one request succeeded in each race. Single owner and matching owner references verified. All marked concurrency fixtures removed; final real state is one user/profile/personal workspace and zero invitations. [Timing evidence](../evidence/S02-concurrency-results.json), [acceptance](../evidence/S02-invitation-race.png), [ownership](../evidence/S02-ownership-race.png).

Frontend verification: S01/S02 unit/component suite 43/43 passed; live anonymous API checks 5/5 passed; Chromium production browser checks 12/12 passed. Lint, TypeScript and production build passed. Browser scenarios cover church creation, invitation copy/revoke, owner transfer/leave, member controls, forged workspace links, sign-in callback handoff, mobile long names/drawer, and the collapsed desktop picker. API fixtures prove UI behavior, not live authorization. Hosted tests above prove role/tenant behavior. A live Google profile also loaded the real membership-backed personal setup page; no church name or teammate was invented. Invitation tokens travel in a URL fragment, are scrubbed on opening, and stay only in this tab’s session storage across Google sign-in. Acceptance is explicit; a failed link remains available for another Google account. Google now opens its account chooser for shared laptops. No invitation email is sent. Personal content is never copied by switching or joining.

Limits: two distinct real Google accounts were not exercised end to end, and phone checks used viewport emulation. Real Google sign-in remains separately verified in S01. The main JavaScript chunk is currently 660 kB (191 kB gzip); split feature routes before release. Full slide editing, presentation and offline preparation remain later sprints.

Security advisor review: no new public privileged function. Private budget table intentionally has RLS with no client policy and no client grants. The existing authenticated identity-bootstrap warning remains intentional and tested. Password leak protection is inapplicable to the disabled email/password provider; no paid upgrade was enabled.

Plan ruling: use transactional database RPCs instead of an Edge Function for invitations. No email dispatch or external service is needed; crypto support already exists in this project. This keeps token creation, budgets, and membership changes in one transaction. Public wrappers are security invoker; privileged bodies are private and explicitly granted. Risk if wrong: invitation delivery/acceptance needs a later adapter, while the public service contract remains unchanged.

Test records will distinguish rollback assertions, temporary concurrency fixtures, UI mocks, and real browser actions. Never reset existing account or church data for tests.
