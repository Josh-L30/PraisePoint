# Church presentation workspace — discovery notes

Status: historical research and discovery record. User approved the revised Liquid Glass visual direction; current requirements and proposed operating rules are consolidated in the written design linked from the root README. Older proposals below are retained as history, not a competing current specification.
Date: 2026-10-26.

## Confirmed requirements

- Brainstorm and plan before implementation; prepare documentation and a sprint plan.
- Use CCF's website as the reference for typography and core palette.
- Adapt Apple's Liquid Glass approach for a smooth, readable interface.
- Show a loading screen before login/signup.
- Frontend: React and Tailwind CSS, developed with Vite and VSCode.
- Database: Supabase; backend recommendation requested.
- Desktop dashboard: collapsible left navigation.
- Primary purpose: create church presentation slides; other features need definition.

### Confirmed during discovery

- Volunteers prepare slides before the service. The current slide and lyric design needs improvement.
- The goal is an attractive website that is free for the church to use. Operational cost limits and font availability remain to be checked.
- Volunteers present directly from the website.
- Presentations must work online and offline because venue connectivity is unknown.
- The presentation setup is a laptop connected to a projector. Volunteers manually advance slides to follow the singers.
- Support pasting a whole song with suggested, editable slide breaks, and manual slide-by-slide lyric entry.
- Include a shared song library so volunteers can reuse lyrics in future services.
- Users sign in with a Google account and have a website profile.
- Signing in permits users to create and present slides without an invitation or administrator approval. This does not yet define access to other users' content or the shared church library.
- First release includes song lyrics, Bible passages, sermon points, announcements, and welcome/closing slides. All five slide categories are confirmed; automatic Bible lookup/import, supported translations, and media capabilities remain unconfirmed.
- First release supports both template-based creation and freeform dragging/positioning of text and images. The earlier template-only recommendation is superseded. This increases the editor's scope and requires dedicated planning before implementation.
- First release includes videos and moving worship backgrounds, in addition to still images. Their exact playback controls, audio behavior, supported formats, upload limits, and device support remain to be agreed.
- Moving backgrounds must continue playing uninterrupted while the volunteer advances through a song's lyric slides; a lyric change must not restart the shared background video. Behavior when switching songs/backgrounds, or using blackout, remains to be designed.
- Zero running cost is a firm requirement, not merely free access for volunteers. Do not assume paid hosting, a purchased domain, paid fonts, paid media services, or automatic upgrades are acceptable.
- User approved Figtree as the zero-cost substitute for Proxima Nova and keeping large videos on the presentation laptop. The CCF-inspired palette remains the visual reference. Shared online media remains limited; local-only media must be transferred/imported separately on other presentation computers.

### Zero-cost feasibility check (2026-10-26)

Current [Supabase pricing](https://supabase.com/pricing) lists 500 MB database storage, 1 GB file storage, 5 GB egress and 5 GB cached egress on Free; projects may pause after a week of inactivity. See also [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing). These are provider limits, not unlimited capacity or an uptime promise. Supabase quotas are shared at the applicable project/organization level, not independently available to every church workspace. A small pilot may fit; usage must be measured before claiming that it does.

Proposed zero-cost architecture: a static React frontend on Cloudflare Pages Free with its provided pages.dev address, Supabase Free for accounts and shared records, and prepared service/media copies on the presentation laptop. See [Pages limits](https://developers.cloudflare.com/pages/platform/limits/) and [provided site addresses](https://developers.cloudflare.com/pages/configuration/serving-pages/). Pages' per-asset limit means it should not be treated as unrestricted video hosting. Local storage and playback still depend on available laptop capacity and existing hardware/internet access.

Approved video storage direction: large videos stay local to the presentation laptop; shared online media is deliberately limited by file size and total quota. Other volunteers need a transfer/import workflow for local-only media. Clearly distinguish shared assets from local-only assets and block offline-ready claims when an asset is missing. Do not silently remove confirmed video functionality or promise automatic cross-device sharing for local-only files. Backend pausing or quotas should not interrupt an already prepared offline service. Exact limits and transfer UX remain design decisions.

Typography decision: the observed CCF typeface, Proxima Nova, is commercial. Its [foundry lists web licensing](https://www.marksimonson.com/fonts/view/proxima-nova/). User approved self-hosted Figtree as the zero-cost replacement, keeping CCF's observed palette and a similar overall typographic character; it is a substitute, not the same font. Retain [Figtree's OFL license](https://github.com/google/fonts/blob/main/ofl/figtree/OFL.txt) when distributed.

No paid service will be activated as part of the zero-cost proposal. Free-tier terms can change; the design must include visible quota handling and portable backups rather than a promise of permanently free unlimited service.

Proposed media boundary: upload video files into the workspace for reliable local preparation; external streaming links are not assumed to work offline. Offline readiness must account for every required video file as well as slides, images, and fonts, and report unavailable assets or insufficient storage. Proposed playback behavior: moving backgrounds loop and are muted by default; standalone videos have explicit play/pause and audio controls. Uninterrupted backgrounds across lyric changes are confirmed. Test video playback on the actual laptop/projector setup, including disconnected operation; no media implementation or device verification has occurred.

Recommended editor design, pending full design approval: one slide canvas supporting templates and customization rather than two separate editors. Use a fixed slide coordinate system so editing, previews, and projected output stay aligned. Proposed essentials include selection, text editing, move/resize, layer ordering, alignment guides, undo/redo, keyboard positioning, readable text defaults, and overflow warnings. These controls are recommendations, not individually confirmed requirements. Canvas dimensions/aspect ratios, image handling, and mobile editing expectations remain open.

Confirmed sharing model: personal workspaces plus shared church workspaces. Users can create and present their own slides immediately after Google sign-in. Personal content is private by default; church songs and service presentations are shared within the church team. Joining a church team controls access to its shared content, rather than the ability to use the website. Membership mechanism, team creation rights, editing permissions, and profile visibility remain to be designed. An invitation link was suggested as a possible membership mechanism, not confirmed as the required implementation. Do not treat Google authentication alone as authorization to modify other people's content.

Proposed song reuse behavior, pending design approval: adding a library song to a service creates a service-specific copy. Adjusting that service's lyrics or slide breaks does not silently change the shared song or another prepared service. Updating the library master is a separate explicit action. Library editing permissions and review requirements remain open.

Recommended offline boundary, pending agreement: volunteers prepare/download a service on the presentation computer while online. A visible readiness check confirms that the app, deck, fonts, and required media are available locally before it says “Ready offline.” Prepared services should reopen and play without a connection, including after a browser restart. First-time login, downloading uncached services, offline editing, and synchronization of offline changes are not yet agreed requirements. External streaming media must not silently count as offline-ready. Browser storage can be cleared or evicted; readiness must be checked again before the service.

Confirmed presentation setup: a laptop connected to a projector with manual slide advancement to follow singers. Proposed interface: operator controls and slide previews on the laptop, with clean audience output on the projector. Keyboard advance/back, clickable slide thumbnails, and a blackout control are proposed essentials; automatic timing is outside the current workflow.

The workspace was empty when inspected. No application has been scaffolded and no dependencies installed.

## CCF research

Inspected the public homepage HTML, generated theme CSS, child-theme CSS, and its linked Adobe Fonts stylesheet. Comments were removed for the final font-variable inspection. This is a source-level inspection, not a browser screenshot or computed-style audit of every component.

Sources:

- [CCF homepage](https://www.ccf.org.ph/)
- [CCF child-theme CSS](https://www.ccf.org.ph/wp-content/themes/bridge-child/style.css)
- [CCF generated theme CSS](https://www.ccf.org.ph/wp-content/themes/bridge/css/style_dynamic.css)
- [Linked Adobe Fonts stylesheet](https://use.typekit.net/dyu3euz.css)

Findings:

- Active child-theme variable: `--ccf-font: "proxima-nova", sans-serif`.
- Body and paragraphs use that variable at weight 400; headings use it at weight 700. Extra-bold utility classes specify 800 and 900.
- The Adobe stylesheet declares Proxima Nova. Raleway, Montserrat, Lato, and other fonts also appear in loaded resources; their presence alone does not establish the primary UI font.
- `#00A6B6` appears in theme accent/hover rules and custom navigation hover styling.
- `#16A5B8` appears in generated button text, border, and hover backgrounds.
- Black `#000000` and white `#FFFFFF` appear in custom styles; gray values also occur in supporting areas.
- These are observed site values, not an official CCF brand manual. WordPress's generic preset palette is not treated as CCF branding.

Recommendation: carry Proxima Nova, teal, black, and white into the proposed direction. Confirm the project's font licensing/hosting arrangement before implementation; do not reuse CCF's Adobe kit ID. Any substitute font needs to be presented as a substitute. Additional surface and accessible text colors will be proposed separately and checked for contrast.

## Liquid Glass interpretation

References:

- [Apple: Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- [Apple: Materials](https://developer.apple.com/design/human-interface-guidelines/materials)

Proposed web adaptation: translucent navigation, a floating toolbar, subtle edge highlights, soft shadows, and restrained blur. Keep slide canvases, reading surfaces, and projected output visually clear. This would be a web interpretation; CSS blur does not reproduce Apple's native material system exactly.

Accessibility and performance requirements to propose in the design: keyboard navigation, visible focus, contrast checks against changing backgrounds, reduced-motion support, an explicit reduced-transparency preference, and an opaque fallback when blur is unsupported or too costly. Browser and device testing remains pending.

Loading concept: a brief brand reveal while fonts and session state initialize, then a smooth transition to authentication or the dashboard for an existing session. Do not impose an artificial waiting period. Provide useful status and recovery on failure; never leave an indefinite animation. Duration and visual treatment remain design decisions.

## Backend options — recommendation pending workflow

| Approach | Fit | Tradeoff |
| --- | --- | --- |
| Supabase Auth, Postgres, Storage, and TypeScript Edge Functions | Recommended starting point for team access, decks, media, and small privileged operations | Requires explicit authorization policies and awareness of function runtime limits |
| Supabase plus a Node.js/TypeScript API or background worker | Consider when reliable server-side deck conversion, heavy rendering, or long jobs are required | Adds hosting, job handling, monitoring, and maintenance |
| Separate full backend from the outset | Consider only if integrations or organizational constraints require it | More infrastructure before the core workflow is proven |

React + TypeScript + Vite + Tailwind CSS is the proposed frontend. TypeScript is a recommendation, not a user-confirmed requirement. VSCode is the editor; Vite is the build/development tool. Git and a shared repository are proposed for collaboration. Hosting, repository provider, budget, environments, and service ownership remain open.

Keep privileged credentials server-side. User-facing database and storage access must enforce team membership and permissions, rather than relying on hidden buttons. No database schema or policies have been designed yet.

Sources: [Supabase architecture](https://supabase.com/docs/guides/getting-started/architecture), [Auth architecture](https://supabase.com/docs/guides/auth/architecture), [Edge Functions](https://supabase.com/docs/guides/functions), [function limits](https://supabase.com/docs/guides/functions/limits). Hosted Edge Functions have bounded CPU, memory, and execution time; heavy export/rendering work needs a separate feasibility check.

## Suggested product contents — not agreed scope

Core candidate workflow: prepare a service → create or reuse a deck → review → export or present → archive for reuse.

Candidate first-release sections:

- Dashboard: next service, recent decks, review requests, and quick actions.
- Presentations: template-based slide editing, ordering, preview, save state, and duplication.
- Confirmed first-release slide categories: sermon points, Bible passages, song lyrics, announcements, and welcome/closing slides. Template behavior and content sources still need design decisions.
- Shared songs: reusable lyrics with both automatic slide-break suggestions and manual slide entry. Sharing is confirmed; search, metadata, and master-edit permissions need design decisions.
- Media library: approved images and backgrounds, with ownership and attribution information.
- Service plans: order of service and links to associated presentations.
- Team/settings: invitations, permissions, branding, and accessibility preferences.

Candidate roles: administrator, editor, reviewer, and presenter. Whether these need distinct permissions must be decided from the real workflow.

Possible later features: version history, simultaneous editing, volunteer scheduling, sermon archive, remote control, and AI-assisted drafts. None are assumed part of the first release. Offline presentation is now required; its precise preparation and recovery workflow still needs agreement. Bible translations and lyric/media sources must be selected with their usage terms in mind; automatic content import is not assumed.

Keep a public church website, giving, pastoral records, and member management outside the initial proposal unless explicitly requested.

## Provisional sprint sequence

These are discussion slices, not implementation-ready commitments or time estimates. Each should ultimately include a complete usable flow and its relevant access, persistence, failure, and recovery checks.

| Slice | Proposed outcome | Depends on |
| --- | --- | --- |
| Discovery | Approve workflow, audience, roles, first-release boundary, and visual direction | Church workflow answers |
| S01 | User signs in with Google, receives a profile, and reaches a responsive dashboard with collapsing navigation | Approved design, sharing/access model, Supabase setup |
| S02a | User creates, saves, reopens, and duplicates a deck using templates for all five slide categories | S01; agreed content sources and slide format |
| S02b | User customizes text and images through freeform positioning with consistent saved, previewed, and projected layout | S02a; agreed canvas controls |
| S02c | User uploads and previews videos and moving backgrounds, with agreed playback and audio behavior | S02a–S02b; agreed formats, limits, and media controls |
| S03 | Volunteer saves/reuses library songs through paste-and-split or manual entry, then arranges a service with decks and approved media | S02a–S02c; agreed content sources and library permissions |
| S04 | Volunteer runs a service directly in the browser using manual operator controls and clean audience output; song backgrounds continue across lyric changes | S02a–S03; agreed media playback behavior |
| S05 | Volunteer prepares a service for offline use, verifies readiness, and presents through disconnection and offline reopen | S04; agreed offline boundary and browser/device support |
| S06 | Pilot team completes a real service rehearsal; address accessibility, performance, recovery, and release readiness | S05; test devices and acceptance criteria |

Browser presentation and offline operation are confirmed requirements. Display setup, offline editing scope, and media requirements may still change the size of these slices.
